# Agent definitions in a client project

`.claude/agents/<name>.md` is generated by `install`/`upgrade` from the Aesir def. Edits to it are overwritten
on the next upgrade. The file starts (after its frontmatter) with a note saying so.

Project lines are not Aesir's (#247, reports#161): the test-suite command in the implementer def is the first command
of `[gates]` `quick` (else `full`, else the first profile) in the client's `aesir.toml`, re-read at every
`install`/`upgrade` (change the config, then upgrade or `upgrade --repair`). With no gate command it says to use the
one in `aesir.toml`. Examples in the defs are single commands (no `cd X && ...`): the CLI is run by absolute launcher
path, so the hook guards allow them.

## Project additions

Put project-specific instructions (for example an extra reviewer checklist item) in
`.claude/agents/<name>.local.md`, e.g. `.claude/agents/reviewer.local.md`:

    - Check that every new endpoint has a rate-limit test.

- Plain markdown, no frontmatter. Commit it.
- `install`/`upgrade` append it to the generated def under a `## Project additions` heading.
- `.local.md` files are never overwritten or deleted. With none, the generated def has no additions section.
- A new or changed `.local.md` takes effect at the next `install`/`upgrade` (which re-renders the defs).

## Researcher (#181)

- `researcher` (Sonnet, own worktree) does design-note and source-reading tasks. Tools: Read, Grep, Glob, WebSearch,
  WebFetch, Write, Edit; no Bash or PowerShell, so no shell writes. It cites every source (URL and quoted passage),
  marks claims no source gives, and reports sources it could not read. The lead commits its files.
- The scope hook treats it like an implementer (task scope) and also refuses Write/Edit outside `docs/` whatever the
  scope says; its own scratch folder and same-project session scratchpads stay allowed (#173).
- `spawn-context researcher --task N --name <agent name>` works as for the other types (`--name` gives the scratch
  path before the agent exists, see below). The agent has no shell, so paste the output into its spawn prompt (header
  line included).

## Waiting, rounds, respawns (#156)

The generated defs carry rule 11 (never block a session; waits go through a Monitor with `python -m aesir wait`).
Supervision of running rounds (`round arm|watch|check`), stop-and-respawn with a `ROUND N CORRECTION` brief and the
rest of the guidance: `docs/supervision.md`.

## Re-spinning an implementer (#129)

A re-spun implementer (or a Workflow one on its auto branch `worktree-wf_<id>-N`) gets a fresh worktree, and the
task branch is checked out in the old one, so it cannot commit to it.

- `spawn-context implementer` (and the SubagentStart hook) adds a `Re-spin:` line when the task's branch exists: the
  agent runs `git switch -c task/<id>-<slug>-r<n> <task branch>` and commits there, keeping the earlier commits.
- Lead: `python -m aesir --as lead task set <id> --branch task/<id>-<slug>-r<n>`. Gates, evidence, review and
  `queue add` then use the new branch; the queue ff-merges it (it contains the old commits) and deletes it. No manual
  git. The old branch and worktree stay for `worktrees` hygiene to clean up.

## Related matches in the brief (#157)

- The brief (hook and `spawn-context`) ends its task block with `Related:`: up to 5 pointers (`D12`, `#034`, or
  `docs/x.md`, then title and one line) to prior decisions, other tasks and design docs on the task's subject.
- Search is by words from the task's title and spec plus the stems of its scope paths, scored over each decision's
  title/context/choice, each task's title/spec and each doc's name/headings/body. A title hit counts double; fewer
  than 4 points is no match; a doc's body counts at most 3 points, so a long generic doc needs a name/heading hit. Docs come from `docs/*.md`, or the dirs in `[project] design_docs` in `aesir.toml`.
- Bounded: 5 lines, one line each, no document text beyond that line. Agents read and cite the matches before a
  diagnosis or fix, and search by subject before telling the owner work is missing.

## After an upgrade (#125)

- Claude Code reads agent defs and hook settings at session start. Running lead/advisor sessions keep the old ones
  until restarted: `upgrade` prints the sessions to restart; `status` (`stale_agent_defs`) and `resume` flag a lead or
  advisor whose recorded checkin is older than the newest file in `.claude/agents`. Subagents use new defs at their
  next spawn.
- Workflow-spawned agents get no SubagentStart `additionalContext` (Claude Code drops it, though the hook still
  creates and binds the agent row). `python -m aesir spawn-context <agent-type> --task N [--name <agent name>]`, run
  from the main checkout, prints the same context: it uses the most recent bound running agent of that type on the
  task (with `--name`, only the row of that name, never another live agent's); with none it prints the context without
  an id and says so.
- Header (#128): `spawn-context` output always opens with `Aesir spawn-context v1 task <N> type <T>`, bound row or
  not. A lead can run it before spawning and paste the output into the spawn prompt; the implementer, reviewer and
  runner defs tell an agent to run `spawn-context` only when its prompt has no line starting `Aesir spawn-context v1`.
  An agent learns its own id from `python -m aesir whoami` (its bound row, read via `AESIR_AGENT`, which the hook
  exports into a bound agent's shell) or from `spawn-context` run after it was spawned.
- Anomaly (#128): when SubagentStart binds a new agent row and the agent's prompt (read from its transcript) has no
  header line, and its transcript is under `subagents/workflows/` (a Workflow agent, whose hook context Claude Code
  drops; Agent-tool spawns get their context and are never flagged, #132), the hook records a friction event `no_context` ("agent started without context: <id> type <T> task
  <N>"). `status` shows these as `no_context_start` (count and latest agent ids) until `status ack no_context_start`;
  a new such start lifts the ack. A prompt that is unreadable at that moment records nothing.

## Scratch folder and stray files (#138)

- Every bound agent gets `<system temp>/aesir/<project name>/<agent id>/` (project name from `aesir.toml` `[project]`,
  else the directory name; `AESIR_SCRATCH_ROOT` replaces `<system temp>/aesir`, used by tests), created at SubagentStart and by `spawn-context` when it finds the bound row. Its context
  has a `Scratch folder:` line naming it and its lifetime. `spawn-context --name <agent name>` (the spawn prompt's
  Agent name) creates the exact folder before the agent is bound, so a Workflow agent (pasted context predates its
  spawn) knows path and lifetime before its first write; the name is normalised as at binding (#248, e.g.
  `implementer-332a`). Without `--name` the line shows the form `<temp>/aesir/<project>/<your Agent name>/`. `python -m
  aesir whoami` also ensures the folder and prints the same line.
- At SubagentStop an unbound agent's folder is deleted when it succeeded, i.e. its final message has the required
  `deviation:` report line; otherwise it is kept (empty folders are removed at once) and swept after `[scratch]
  keep_failed_hours` (default 24) by the next spawn or stop. A task-bound agent's folder (#275) is kept even after a
  clean finish, until its task is merged, verified or wontfix, at most `[scratch] keep_bound_days` (default 14, D234)
  so a task that never closes cannot keep it; a failed bound agent also waits out `keep_failed_hours`. A task row that
  is missing or unreadable gives the `keep_failed_hours` rule. A running agent's folder is never swept. Put outputs a
  later agent needs in the task's `docs/`, not the scratch folder. Fail-open: a problem here is a hook_failure friction event, never a block.
- A gate, `evidence run`, the merge queue or a long run refused for a dirty tree lists each file with its modified
  time and the agents the registry says were running then, to find the writer.
- Friction `stray_write`: a worktree agent's Bash/PowerShell command redirecting (`>`, `>>`, `tee`, `Out-File`) to an
  absolute path in the main checkout. Never denied.
- #164/#168 redirect guard (denied): a subagent's redirect/`tee` into the main checkout. A relative target is resolved
  against the cwd moved by any `cd` before it, so `cd <main> && x > rel` and `> ../rel` landing in main are refused;
  a `cd` to a directory outside main still exempts it.
- #168 HEAD guard (denied): a subagent's `git checkout|switch|reset|rebase|merge|pull|cherry-pick|revert|stash
  pop/apply` whose cwd, `cd`, or `-C` target is the main checkout. The message names `git show <ref>:<path>`,
  `git diff A..B`, `git log <ref>` and the agent's worktree. Read-only git and `git -C <own worktree> ...` pass; main
  sessions are not affected. `queue run` refusing a main that is not on main names the ref and the HEAD reflog entry.
- #235 kill guard (denied): a subagent's process kill by name, image or command-line pattern (`pkill`, `killall`,
  `taskkill /IM|/FI` or `//IM`, `Stop-Process -Name`, `kill $(pgrep ..)`, `xargs kill`, `wmic .. where name=..`), also
  inside `bash -c`, `cmd /c`, `powershell -Command` and loop/`if` bodies. A kill by PID is allowed only when that
  process's working directory is inside the agent's worktree or scratch folders; otherwise the message names the
  process cwd. A PID that is a variable (`$p`, `$!`) is refused; `$(cat run.pid)` is read. In git-bash `kill N` takes an
  msys PID, mapped to the Windows PID through `ps -p N` (WINPID column, ~0.2 s) before the cwd check; an unmappable PID is
  refused, an msys PID `ps` does not list is gone. `taskkill`, `Stop-Process`, `kill -W/-f` use Windows PIDs. Lead and
  advisor sessions are not affected. Text that merely mentions kill (`grep kill`, `echo pkill`, heredocs) passes.

## Notes to a running subagent (#141)

`python -m aesir --as lead note <agent-id> "<text>"` stores a steering note for a running agent. The PreToolUse hook
pushes it into the agent's context (additionalContext, marked "from <sender>") on the agent's next tool call and
marks it delivered; the agent does not poll. If the agent ends first (SubagentStop), undelivered notes are expired and
the sender gets a reply in their inbox per note ("never delivered"). Delivered notes stay as history (`thread <task>`).
The agent answers with `reply M<n> "<text>"`, which goes to the sender. A denied tool call delivers nothing; the note
waits for the next call. A db error never blocks the call: it logs and adds a `hook_failure` friction event (D115).

- #172: a note repeats (short form) on every tool call of the agent until it replies, and while one is unanswered its
  Bash/PowerShell `git commit` and `git push` are refused, naming the note ids; other commands run. Reply to every
  note before committing. Delivered-but-unanswered notes stop repeating when the agent ends. Leads steer with
  `aesir note <agent-id>`, never a checkpoint file (state stays in the db).
- Steer a running agent: `aesir note <agent-id> "<text>"` (ids: `aesir agent list`). The target may also be `#N` or
  `task/N-slug`: it resolves to the one running agent bound to task N, and is refused naming the candidate ids when
  several run (#207).
- Workflow agent rows (#207): a row adopted without a task learns it at the agent's next tool call from, in order,
  its worktree branch `task/N-*` and a spawn-context header it read (the FIRST line of a tool result in its own
  transcript; headers merely quoted in text or files never bind). Binding starts the task (#182) and attaches the
  agent's earlier notes and replies to it. `aesir agent bind <agent-id> --task N` does the same by hand (logged on
  the task). A prompt line `Agent name: <role>-<task>-<letter>` (e.g. `implementer-238-a`) names the row, if it carries
  the task number and is free; else the generated id is used. The prefix is free text (`checker-261-a` for a reviewer):
  role, scope and `--as` limits come from the recorded agent type, never the prefix, so a persistent role name or another
  type as prefix (`lead-..`, `implementer-..` for a reviewer) is refused and the id generated (the hook warns). A row's model is read from
  that agent's own transcript (first assistant message), never a default.
- Use notes for steering: stop, a file moved, skip X. A change to what the task must do goes on the task's spec
  (`task set`), not a note, so the reviewer and builder judge against the same spec.
- Delivery relies on Claude Code honouring PreToolUse `additionalContext` for subagent tool calls (SubagentStart's is
  dropped for Workflow agents, #128); a note shown nowhere still reads as delivered, so ask for a reply when it matters.

## Verifying a task: read the logs (#158)

The requester (advisor) reads every evidence log before `task set N --status verified`. `[OK]`/RAN means the command
ran (exit 0), not that the criterion is met; only the log shows that. `task show N` ends its evidence block with the
log path per criterion, and `task set N --status verified` prints the same list. A criterion whose log is missing or
does not show the claim met is not verified: send the task back.
