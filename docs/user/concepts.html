A P3D file in Houdini

A P3D file is the model format of Arma 3. Object Builder writes it. One file holds several LODs (levels of detail): separate versions of the model for different jobs. Some are for looking at (Resolution 1 is the most detailed, Resolution 2 is simpler and is used farther away). Others are for the game engine: Geometry is the collision shape, Memory holds named points such as where a muzzle is, Shadow Volume casts shadows.

Houdini has no such thing as a file with several models inside, so the add-on uses two shapes of geometry. Both are ordinary Houdini geometry. Geometry in Houdini is points, polygons and the extra data attached to them.

P3D geometryThe whole model. It has one packed primitive for each LOD, in file order. A packed primitive is a whole piece of geometry stored as one item, with its own place in space. Packed items cannot be edited point by point until you unpack them. Each item has a name such as Resolution 1 or Geometry. P3D Import and Assemble LODs output this.
LOD geometryOne LOD as ordinary, unpacked points and polygons. You edit this. Extract LOD makes it from the P3D geometry, and Assemble LODs packs it back.

Most A3OB nodes work on a LOD geometry. P3D Export and Validate accept either shape. If you give them a LOD geometry, they write a file with just that one LOD.

To see the packed items, open the Geometry Spreadsheet (a pane that lists the points, primitives and attributes of the selected node) on the Primitives tab. You will see one row for each LOD.

Why two shapes?

A Houdini node that merges several pieces of geometry loses the per-piece data of all but the first. LOD data is per piece, so LODs have to stay packed until you want to edit one. Edit one LOD at a time, then let Assemble LODs put it back. The Replace Matching LODs switch matches an edited LOD to the original one of the same stored resolution signature and keeps its place in the list. LODs with no match are added at the end. LODs you did not touch pass through unchanged.

Coordinates

Up is Y in Arma and in Houdini. The model's left stays on the same side. Arma's Z axis points the other way from Houdini's, so the importer negates Z and the exporter undoes it. The order of the corners of each polygon is reversed in the same step so that the front of every polygon stays the front. UV coordinates are flipped from top-down to bottom-up. You do not have to do anything. A character that looks forward in Object Builder looks toward +Z in Houdini.

LOD data and properties

An attribute is a named piece of data attached to points, polygons or the whole geometry. Data attached to the whole geometry is a detail attribute. A LOD geometry keeps its LOD information in detail attributes. All attribute names of this add-on start with a3ob_.

Selections

A selection in Object Builder is a named set of points, and often the faces made of them. Animation, hit zones, components and memory points all use selections. In Houdini a selection is a group: a named set of points (a point group) or polygons (a polygon group).

  • Points. The selection is a point group with the same name.
  • Weights. A selection can give each point a weight (how strongly it belongs, used for animation). Weights are kept in a point attribute a3ob_w_ followed by the name. It is only made where some weight is not 1.
  • Faces. In a P3D file a selection also says which faces belong to it. The importer makes a polygon group for this only where the faces are not simply "all corners are in the selection". Otherwise the faces follow the points. The Explicit Face Groups switch of P3D Import makes a polygon group for every selection.

Names. Houdini group names may only hold letters, digits and underscores. Object Builder names can hold anything, such as -proxies or proxy:\a3\.... The add-on stores such a name in a reversible code that starts with xn__. For example -proxies is stored as xn__proxies_cka. Plain names like head are stored as they are. The code is turned back into the real name when the file is written. The Selection browser shows the real name next to the stored one, copies the stored one for you to paste into a group field, and can add nodes that create, delete or rename a selection.

What becomes a selection on export. Every point group, except names that start with two underscores. This is the Selection Mask parameter of P3D Export. A group that came from the file is always written.

Components. A Geometry LOD is built from convex pieces. Each piece is a selection named component01, component02 and so on. Arma needs at least one. The starter network has one. The Auto-Components option of the export can make them for you when none exist. The Components node makes the groups in Houdini, so you can see and edit them: one for each closed connected piece, or one for the convex hull of each piece.

Proxies

A proxy is a place where the game puts another model: a weapon on a slot, a seat for a crew member, a backpack. In the file it is a selection named proxy: plus the model path and an index, on a single triangle. The triangle gives the position and direction of the other model. The path and index must be unique within a LOD.

In Houdini the importer makes each proxy a small packed primitive inside the LOD geometry. It has a path attribute (a3ob_proxy_path) and an index (a3ob_proxy_index), and you move it with an ordinary Transform node. A proxy that cannot be packed without losing something stays as a plain triangle with the same two attributes. The Proxy node adds new proxies, one by hand or one for each point of a second input. A proxy has a position and a rotation but no size.

Mass

The Geometry LOD gives each point a mass in kilograms. The game adds them up to get the weight of the object and works out its balance. In Houdini this is a point attribute, a3ob_mass. The Mass node sets it. Houdini has its own attribute called mass for simulations; the add-on does not use it by accident. The Mass node can copy between the two if you want that.

Modes of the Mass node: Set on each gives every point the same mass, Uniform total shares a total weight equally between the points, From density works from a density and the volume of each closed piece, and Clear removes the mass. See Mode in the reference.

Textures, UVs and sharp edges

  • Textures and materials. Each polygon has two text attributes, a3ob_texture and a3ob_material (the rvmat file). They hold the text exactly as in the file, including procedural textures such as #(argb,8,8,3)color(...). The Material Assign node sets them for a group of polygons. Only the toggle Show in Viewport touches Houdini's own material attribute (shop_materialpath), to show the texture in the viewport; the export ignores it. A .paa is shown from a .png, .tga or .tif of the same name next to it, else from a picture decoded from the .paa. The rvmat is not shown. On export, when Write Textures as .paa is on (it is in the Arma 3 release preset, not in Lossless), every texture path that does not end in .paa is written with .paa (camo1_co.png becomes camo1_co.paa); the .paa itself must exist when you build the add-on, and making it is your job. With it off, texture paths are written exactly as they are. A run of polygons that share a texture and material is a section in Object Builder. Sections are decided by polygon order, so assigning materials to scattered polygons splits them. The Sort Sections option groups them on export.
  • UVs. UV sets are vertex attributes: uv for the first set, then uv2, uv3 and so on.
  • Normals. The shading directions are kept as the vertex attribute N.
  • Sharp edges. The edges that Object Builder marks sharp are the edge group a3ob_sharp.

Game paths: the P drive, HEMTT and the project root

Arma tools expect your source files on a virtual drive, usually called P: (the P drive). A texture that lives at P:\my_mod\data\crate_co.paa is known to the game as my_mod\data\crate_co.paa. The part that stands for the drive is the project root, by default P:\.

The Relative Paths option turns the full path of every texture, material and proxy file into the path the game uses, when a file is written. For each path it tries these four steps in order, and the first one that fits wins:

  1. A $PBOPREFIX$ file. The add-on looks in the folder of the file, then in each folder above it, for a file called $PBOPREFIX$. The nearest one gives the prefix: the text of its first line (a file with key=value lines is read by its prefix line only). The rest of the path below that folder is added to the prefix.
  2. A HEMTT project. If there is no such file, the add-on looks above the file for a folder with .hemtt/project.toml. If the file lies in addons\<name> of that project, the prefix is mainprefix\prefix\addons\<name>, built from the two values in project.toml, which is how HEMTT names the addon.
  3. The project root. Otherwise the project root is cut off the front of the path.
  4. The drive letter. If the file is not under the project root either, only the drive letter is removed (a path that starts with \\server is kept as it is). The export warns you, because the result is probably not the path you want.

Example with a HEMTT layout. The folder addons/props holds a $PBOPREFIX$ file with the line mymod\addons\props. A texture at ...\addons\props\wallScreen\camo1_co.paa is written as mymod\addons\props\wallScreen\camo1_co.paa. Without that file, a project.toml with mainprefix = "mymod" and prefix = "stuff" would give mymod\stuff\addons\props\wallScreen\camo1_co.paa instead.

Typing the in-game path directly also works: a path with no drive letter, such as mymod\addons\props\wallScreen\camo1_co.paa, is kept as typed (apart from one leading backslash, which is dropped).

The project root (step 3) comes from the Project Root parameter of the export node. If that is empty, it comes from the Project root and presets shelf tool. If that has none either, it is P:\. You can also set the environment variable A3OB_PROJECT_ROOT, which wins over the shelf setting.

The shelf tool stores its settings in one file, a3ob_settings.json, in your Houdini preferences folder. Set the environment variable A3OB_SETTINGS to use another place.

Presets

A preset is a saved set of export options. Pick one in the Preset menu of a P3D Export node and press Apply to fill in the options. Quick Export and Batch folder convert take a preset by name. Two presets come with the add-on. You can save more with the Project root and presets tool.

Lossless turns every option that changes data off. Arma 3 release is the set that Object Builder uses by default. The two Czech and Renumber options are off in both, as in Object Builder. Duplicate LODs stays on Fail in both. A preset does not change Project Root or Keep a .bak.

Triangulate Where Needed is on in both presets, because a P3D face has 3 or 4 points and the game wants triangles in some LODs. The export runs Houdini's own Divide (Convex Polygons on, Maximum Edges 3, Avoid Small Angles on) on the bad polygons of each LOD and leaves every other polygon as it is, so a model that already passes is written exactly as before. Groups, UVs, textures and materials carry over to the new triangles. The geometry on the node does not change, and each LOD it touched gets a warning with the number of polygons. A Divide node placed after Assemble LODs cannot do this, because it sees the packed LODs, not the polygons inside. To control the result yourself, put a Divide on the LOD's own branch before Assemble LODs. The Validate node has the same switch in its LOD Rules tab. Switch it off and the checks report those polygons as errors or warnings, as before.

Choosing a preset in the menu changes nothing by itself: press Apply. After Apply you can still switch single options on or off on the node. Each option has a full entry in the P3D Export reference.

Rigging

A character in Arma 3 moves with a fixed skeleton: the same bones, with the same names, for every soldier. The Rig Skeleton node builds that skeleton in Houdini as a KineFX skeleton, so Rig Pose, Joint Deform and the other KineFX nodes can use it. It needs two files.

  • A model.cfg. It lists the bones, each with its parent, in a CfgSkeletons class. A file can hold several classes: pick one in the Skeleton menu. The node reads exactly the file you pick. Arma itself also reads a <foldername>.cfg (it wins over model.cfg) and a <modelname>.cfg, so if your skeleton is in one of those, pick that file. #include lines are not followed.
  • A pivots .p3d file. It says where each joint sits. The model.cfg only names the game's own pivots file (pivotsModel), which is packed and can't be read, so you point at an editable copy. Its Memory LOD has one selection per bone, and the first point of the selection is the pivot. The Arma 3 Samples have one: ManSkeleton_Pivots.p3d.

Set the Arma 3 Samples folder once in the Project root and presets tool (it finds the Steam folder by itself when it exists). A new Rig Skeleton node then starts from the Samples files. Each joint is named as in the model.cfg and sits at its pivot. The face bones (Face_*) and the eyes are left out. A bone with no pivot (the Samples have none for Camera, weapon and launcher) is left out and listed on the node, and a pivot that is not a bone (the Samples' Hips) is ignored and listed too.

Bone weights: selections and capture weights

The same bone weights can live in two forms.

  • Selections. This is what a P3D file holds and what P3D Import makes. Each bone has a selection (a point group named like the bone) and the weight of each point is in a point attribute a3ob_w_<bone>. P3D Export writes this form.
  • Capture weights. This is what the KineFX nodes (Joint Deform, Rig Pose) use: the point attribute boneCapture.

The Weights Convert node changes one form into the other for the skeleton on its second input. Only selections whose name matches a joint (upper and lower case don't matter) are bone weights. A component, a hidden selection or a proxy selection is left alone. Capture to Selections names a selection like the joint in the model.cfg (head, not Head) and renames an existing one; the option "Keep existing spelling" leaves the names as they are. A member with weight 0 (byte 255 in the file) counts as no weight.

The Weight Cleanup node makes the selections follow Arma's rules, and you run it before P3D Export. It changes only the bone selections, in this order:

  1. Weights below Prune Below (0.01) are dropped. A point never loses its heaviest weight.
  2. Only the Max Bones per Point (4) heaviest weights stay.
  3. The weights of a point are scaled to a sum of 1, and snapped to steps of 1/254, as in the file. The sum is exactly 1.

If the skeleton's model.cfg class has isDiscrete = 1, every point keeps only its heaviest bone with weight 1. The point attribute a3ob_rig_changed says how much the weights of each point changed (0 means not at all), and the node message gives the counts, the points with no bone weight (a warning) and the members with weight 0. Points whose weights already followed the rules, like most of the Samples character, don't change.

P3D Export writes the weights as they are: it never changes them. Three switches on the LOD Rules tab of P3D Export and Validate warn when a point breaks the rules: At most 4 bones per point, Bone weights add up to 1 (within one step of 1/254) and Every point has a bone weight. These two nodes have no skeleton input, so a selection counts as a bone selection when its name is one of the bones of the standard Arma 3 man skeleton (OFP2_ManSkeleton, upper and lower case don't matter). A model with another skeleton is not checked. The checks look at Resolution, view and shadow LODs only, and each message tells you to run Weight Cleanup.

The checks: errors and warnings

The Validate node and the cook of P3D Export run the same checks, so a model that passes one passes the other. Each message starts with the LOD name and ends with how to fix the problem.

  • An error means the file cannot be written correctly. The node turns red, the nodes below it stop, and Save to Disk writes nothing.
  • A warning means "look at this". The node turns yellow, the data keeps flowing, and you can still save.
  • Errors Show As can turn errors into yellow warnings (the text still starts with Error). Warnings Count As Errors does the reverse, for a strict check before a release. Saving always stops on a real error.
  • A node shows at most 25 messages (Max Messages). The rest are counted, and listed in Windows > Log Viewer (source A3OB).

Besides these, the checks include rules for the shape of each LOD type: Geometry (convex, contiguous, components, mass), Shadow Volume (triangles or convex quads; the usual-resolution and LODNoShadow rules are off by default), point LODs (no edges or faces), Roadway, Paths and more. Every such rule has its own switch on the node, named like Triangulated (on the LOD Rules tab), so you can turn off a rule that does not suit your model. The rule's id, such as T2-TRI, ends its tooltip and appears in the messages. The Validate reference lists them all with their meaning. The node's Check LOD-Type Rules switch turns all of them off at once.

Shadow and underground LODs are always written with hard edges. Every export does this, with every preset, and there is no switch for it: every edge of these LODs goes into the sharp edge list of the file, and each polygon gets its own face normal. The message "Shadow Volume 0: all edges written as sharp (shadow LODs need hard edges)" says it happened. A LOD that was already sharp is written unchanged, and you get no message. The geometry in Houdini is not changed, only the file.

Lossless round trips

A round trip means reading a .p3d file into Houdini and writing it out again. With the Lossless preset and no edits, the new file is identical to the old one, byte for byte. This holds for the two sample files in the add-on folder and for all 34 files of Bohemia's Arma 3 Samples. Nothing in the file is thrown away on the way through, even data Object Builder does not show: blocks of data it does not understand, selection weights that Object Builder itself would lose, and the stored LOD signatures are kept.

What stays identical, and why

Object Builder writes some things in a layout that Houdini geometry cannot hold. When you import a LOD, the add-on stores that layout in a small hidden record on the LOD (a detail called a3ob_layout). You never see it as a selection, and it is not an attribute you edit. It covers:

  • the table of normals, including entries that repeat a vector;
  • the unused fourth slot of every triangle;
  • the order of the sharp edge pairs, including pairs that are not edges;
  • the order of points and faces when proxies sit between the other points and faces;
  • the sign of a zero in a position.

Extract LOD and Assemble LODs pass the record on unchanged, so a LOD that goes through them and was not edited still comes back identical.

When it falls back

The record belongs to the positions and the faces it was taken from. If you move a point, delete or add a face or point, or reorder the faces (the Sort Sections option does), the record no longer fits. The export then ignores it and writes the LOD in its own plain layout: one table entry per different normal, zero in the unused slots, and so on. The content is still the same, and the file is valid. You get one info message that names the LOD. Edits that do not change positions or faces, such as materials, flags, selections or properties, leave the record valid. If you edit the normals, the layout of everything else still comes back.

Other cases

  • A LOD that did not come from an import (made by hand, or by New P3D) has no record. It is written in the plain layout, with no message.
  • A face with fewer than three points is dropped on export, with a warning, because the file writer cannot write it.
  • A proxy that you moved is written from its new position. A proxy that you did not touch is written as it was read.
  • Data that depends on the number of points or faces (for example a stored sharp edge that is not a polygon edge) is dropped, with a warning, if you add or remove points.
  • Every option in a preset that changes data, such as Lowercase, makes the file differ on purpose.

The Batch folder convert tool is a quick way to test the round trip on a whole folder of your own files. It writes every file again into another folder and reports for each one whether it is identical, different or failed. It never writes into the folder it reads from.
